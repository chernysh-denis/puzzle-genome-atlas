## Basic data

- Release / origin: Built by Gabriele Cirulli over a weekend and released as an open-source browser game in March 2014. Cirulli describes it as directly based on Veewo Studio's `1024!` and Sami Romdhana's earlier `2048`, and indirectly descended from `Threes!`; he says he did not know about `Threes!` while building it.
- Platform: Originally JavaScript in a web browser, with keyboard and touch/swipe input; official mobile apps followed.
- Puzzle family: Stochastic single-player slide-and-merge / board-compression puzzle.
- Unit of analysis: Cirulli's original 4 × 4 version, not later clones or variants.

## Mechanical decomposition

- Elementary player actions:
  - Choose one of four global slide directions: up, right, down or left.
  - Restart after failure or at will; after first reaching 2048, choose either to stop at the win state or keep playing.
  - The player does **not** select individual tiles or directly command a merge. One input acts on every movable tile.
- Automatic system behaviours:
  - All tiles traverse as far as possible in the chosen direction until stopped by the boundary or another tile.
  - Two colliding tiles of equal value merge into one tile with double the value.
  - Resolution is ordered from the leading edge. A produced tile cannot merge again during the same move; therefore `[2, 2, 2, 2]` moved left resolves to `[4, 4, 0, 0]`, not `[8, 0, 0, 0]`.
  - Every **valid** move adds exactly one tile to a random empty cell: value 2 with probability 0.9 and value 4 with probability 0.1. A direction that changes nothing does not spawn a tile.
  - The score increases by the value of every newly merged tile.
- Constraints:
  - Fixed 4 × 4 board: at most 16 occupied cells.
  - Equal-value requirement for merging.
  - Global coupling: a directional input affects all rows or columns, so a desired local merge cannot usually be isolated.
  - One-merge-per-produced-tile limit within a move.
  - A new low tile consumes one empty cell after every valid move.
  - No preview of the next tile's value or location and no undo in the original implementation.
  - Only four candidate inputs, sometimes fewer because no-effect inputs are invalid.
- Information model: The current board, score and best score are visible. Slide/merge resolution is deterministic for a chosen direction, but the next tile's value and position are hidden random future information. This is **not** perfect information over the next state.
- Time model: Static turn-based input with immediate automatic resolution; no timer and no opponent.
- Objective:
  - Explicit milestone: create a 2048 tile.
  - Continued objective: after reaching 2048, the original interface permits continued play for a higher tile and score.
  - Evaluation: accumulated merge score plus highest tile; the implementation also stores best score locally.
- Failure condition: No empty cell and no orthogonally adjacent equal pair, so none of the four directional inputs can change the board.
- Rule evidence: [P2] implements two starting tiles, the 90/10 spawn, directional traversal, collision merging, score, win, post-win continuation and the exact no-moves test. [P3] supplies the player-facing goal and merge explanation. [A2, §1] independently formalises the traversal order, valid move, spawn, score and terminal state.

## Strategic depth

- Local decision: Choose the direction that creates immediate merges or opens cells while accounting for every other line moved by the same input. The immediate reward is visible, but a high-scoring merge can still damage the ordering of larger tiles.
- Medium-term planning: Build mergeable pairs without separating them behind unmatched values; preserve enough empty cells to reposition lines; control which directions remain safe. The random spawn makes this contingent planning rather than a fixed solution path.
- Long-term structure: Keep large values spatially ordered, normally with the maximum near an edge/corner, and feed smaller values toward it. [A1] reports that useful evaluation functions reward monotonic rows/columns, smooth neighbouring values, empty cells and maximum tile value; rewarding monotonicity tends to collect high values in a corner.
- Scarce strategic resource: **Maneuverable empty space**, not score. Empty cells permit global shifts and recombination; each valid move spends one cell through spawning, while merges recover cells. Ordering is a second scarce resource because a misplaced large tile is difficult to move past.
- Common discovered heuristics:
  - Preserve empty cells.
  - Maintain a monotone or snake-like value gradient.
  - Anchor high tiles near one corner and avoid inputs that pull the maximum out of the ordered edge.
  - Prefer adjacent values that are equal or close enough to become mergeable soon ("smoothness").
  - Evaluate the board after the spawn risk, not only the immediate merge score.
- Evidence boundary: [A1] shows these board properties are useful to AI evaluation and that search informed by them outperformed unguided MCTS in its experiments. That supports their strategic relevance, but it does **not** prove that one fixed "corner strategy" is optimal for human play. [P5] also criticises the target 2048 as too easy under a repetitive corner policy; that is designer testimony and a counterpoint to claims of uniformly deep play, not a formal optimality result.

## Why decisions have consequences

A move has three coupled effects:

1. it compresses all four lines on one axis;
2. it deterministically changes tile order and recovers space through merges;
3. it exposes a set of empty cells into which an unpreviewed 2 or 4 can spawn.

This creates the Atlas pattern in H-002: an attractive present merge may reduce future structure. It also explains why keeping an empty cell is not merely delay; it preserves access to future rearrangements.

## Replay structure

- What changes between sessions: The locations and values of the two starting tiles, then the value and location of every post-move spawn.
- Randomness: Explicit and continuous. The original code uses a 90% / 10% choice between 2 and 4 and chooses a random available cell.
- Procedural generation: No authored or generated levels. Replay variation is emergent stochastic state evolution from the same rules and board geometry.
- Multiple viable strategies: There are many viable move sequences, symmetric choices of anchor corner and several algorithmic policy families (expectimax, averaged depth-limited search, MCTS and learned value functions). Evidence is insufficient to claim that several sharply distinct human macro-strategies are equally strong; corner/monotonic ordering appears dominant in the sources reviewed.
- Typical reason for replay: Improve best score or maximum tile, test a cleaner board-ordering policy, and recover from a recognisable structural collapse. This is a medium-confidence inference from the visible best-score loop and fast restart, not a measured player-study result.

## Player trust

- Can failure be understood? Mostly. The complete current board is visible, deterministic movement can be mentally simulated, and terminal failure has a clear board-level condition. Players can often trace collapse to lost empty space, broken ordering or a direction that displaced a large tile. Attribution is not perfect because an unpreviewed spawn can materially worsen a position.
- Does progression remain believable? Yes for the analysed original: there is no stat progression or adaptive level curve. Improvement is expressed through player skill, score and maximum tile; the same rules remain in force throughout.
- Artificial walls? None in the original open-source core. There are no payments, energy, level gates, difficulty tuning or forced retention systems in [P1–P3]. The only wall is the board state produced by decisions plus random spawns.
- Trust caveat: "No artificial walls" applies to Cirulli's original version only, not the many third-party 2048 apps.

## Adjacent games

- Direct predecessors:
  - `1024!` by Veewo Studio: Cirulli's stated direct influence.
  - Sami Romdhana's earlier web game also named `2048`: Cirulli's repository says his version was based on it.
  - `Threes!`: indirect design ancestor. Cirulli says he learned of it only after building his version; the `Threes!` creators document the sequence `Threes!` → `1024!` → `2048`.
- Variants:
  - Deterministic 2048, in which spawn position/value are fixed.
  - Fibonacci-value merging.
  - Larger boards and higher target values.
  - Endless play beyond the 2048 milestone, already supported by the original implementation.
- Similar games:
  - `Threes!`: tiles move at most one cell per input, base tiles combine asymmetrically, and the next tile is previewed; these differences create a related but non-identical decision structure.
  - `1024!`: full-distance slide-and-merge with a fixed central obstacle according to [A2].
  - `Fives`: a close `Threes!` rules variant rather than a 2048 reskin.

## Atlas classification

Primary loop:

`Global directional slide + ordered collision/merge resolution + random spawn after valid move + 16-cell board space`

Layered form:

| Atlas layer | 2048 mechanic |
|---|---|
| Player action | Choose one global slide direction. |
| Automatic response | Compress lines; merge equal collisions once; score; spawn one random 2/4. |
| Constraint | 16 cells, equal-value compatibility, global coupling, no next-spawn preview. |
| Objective / evaluation | Reach 2048; then maximise tile and accumulated merge score. |
| Information | Visible current state plus hidden random future spawn. |
| Time | Turn-based with automatic resolution. |

Classification correction: `Merge + spawn + limited space` is too coarse for 2048 because it incorrectly presents merge as the commanded action. `Merge` can be an elementary action in a game where the player explicitly selects objects to combine; here it is collision-triggered system resolution.

## Hypothesis implications

- **H-001 — supported as a case, not proven generally:** the rule set and geometry remain fixed while random spawns and player history create changing positions.
- **H-002 — strongly instantiated:** immediate merge value can conflict with board order and future maneuverability.
- **H-003 — partly supported:** structural mistakes are legible, but spawn randomness weakens complete failure attribution.
- **H-004 — supported for the original version:** there is no character-stat progression; mastery is recognition, planning and risk management.
- **H-005 — needs a role-sensitive refinement:** the same verb (`merge`) can be an action in one game and an automatic behaviour in another.

## Open questions

- How much of expert human performance is explained by corner anchoring versus deeper spawn-risk planning?
- How often do players attribute loss to their last recognisable structural mistake versus an unlucky spawn?
- Does previewing the next tile, as in `Threes!`, increase perceived agency enough to offset added information load?
- Which board metrics best predict human-readable danger: empty-cell count, mobility, monotonicity, smoothness or maximum-tile position?
- Does the 2048 milestone shorten perceived mastery because a repetitive policy can often reach it, as [P5] argues, while endless score play remains much deeper?
